# agentic_scripts — Load-Aware Agentic Workflows Plan

**Purpose:** Timer-gated, load-aware automation: OC-todo resolver and mail-keeper workflows driven by headless OpenCode.

## Objective

Build `agentic_scripts` into a small Python project of autonomous workflows that run on this 24/7 server only when it is idle. Two workflows ship now: (1) an **OC-todo resolver** that scans a configurable set of GitHub repos across all branches for `OC-todo:` comments and opens one pull request per resolved todo via a headless OpenCode agent; (2) a **mail-keeper** workflow that indexes the local maildir backup (13,088 messages), triages new mail, and keeps the `ARP_roadmap` admin vault up to date — provenance-tagged people/project notes and tracked todos — while draft replies are saved locally as files (never sent); vault changes are committed on a feature branch per git-workflow for human review. Success = a fresh setup script brings the system up; with the gate open, each workflow produces its observable outputs idempotently; with the gate closed, runs exit as no-ops without touching any repo. Future workflows plug in as new registered modules without scheduler changes.

## Functional Tasks

### Task 1: Load-Aware Scheduler Core (shared foundation)
- **Goal:** A single entry point, invoked by a timer, that decides whether the server is idle enough and, if so, runs the registered workflows one at a time. When idle is not confirmed, the run is a fast, logged no-op. Every run is auditable afterwards.
- **Why this approach:**
  - **[Decision: gate = hybrid window + load]** Value = quiet time window (default 22:00–08:00, crosses midnight) AND 1-min load average below a threshold (default 2.0) sustained across 2 consecutive polls (~30 min apart, stored between polls in the state area) because user chose hybrid gating (2026-10-14) and the rig serves interactive LLM inference during the day — a single low-load sample can be a transient dip (own analysis; 24/7 rig context in /workspace/Research/ai-agent-workflow/).
  - **[Decision: timer + self-check, not a daemon]** Value = a timer (default every 30 min) invokes a stateless entry point that performs the gate check itself, because user chose timer + self-check over a resident daemon (2026-10-14). The entry point is deliberately timer-agnostic so a daemon or manual `--force` run reuses the same gate logic.
  - **[Decision: trigger mechanism]** Value = cron entry on this machine (cron package installed by setup; verified not present 2026-10-14) plus a systemd timer/service unit shipped for real systemd hosts, because this container has no init system (PID 1 = `bash`, verified) — cron is the smallest reliable recurring trigger available here (own analysis of the verified environment; prior art: /workspace/scripts/email-sync/setup-timer.sh already implements the systemd→cron detection for the v1 pipeline).
  - **[Decision: load source]** Value = `/proc/loadavg` (via psutil) because inside the container it still reports host-kernel load, which is what "server load" means (own analysis; psutil verified present).
  - **[Decision: exclusivity]** Value = an exclusive file lock with skip-if-held semantics (no queueing): if a timer fires while a run is active, it logs and exits, because agent runs can outlast the 30-min interval and overlapping runs must never double-process (own analysis; idempotency is also enforced per-workflow in Tasks 3–4).
  - **[Decision: logging]** Value = per-run log files in a gitignored log area plus a short human-readable last-run summary, because automation that acts on repos and mail must be auditable without a dashboard (own analysis).
  - **[Decision: testability]** Value = `--force` (bypass gate) and `--only <workflow>` flags, because acceptance testing must not wait for 22:00 or for the server to idle (own analysis).
- **Acceptance criteria:**
  - With load above threshold or outside the window, the entry point exits 0 within seconds, logs the gate inputs (time, load1/5/15, window state) and a "gate closed" verdict, and changes nothing on disk in any repo.
  - Two simultaneous invocations never run workflows concurrently (second logs "already running" and exits).
  - Each run's log records, per workflow: triggered/skipped, items found, actions taken, errors.
  - A new workflow can be enabled by adding it to the configuration's registered list without modifying scheduler logic.

### Task 2: Project Foundation
- **Goal:** A Python package that both workflows share: validated configuration, durable per-workflow state, git helpers, an agent-runner wrapper, and the mail reader — so future workflows are additive modules.
- **Why this approach:**
  - **[Decision: stack]** Value = Python 3.12 managed by `uv`, `src/` layout, Ruff for lint/format, pytest for tests, because this is the adopted 2025/2026 stack and the machine already has `uv` 0.12.5 + Python 3.12.3 (research: /workspace/Research/ai-agent-workflow/repo-file-conventions-best-practices.md; verified locally 2026-10-14).
  - **[Decision: configuration]** Value = one declarative config file (YAML) with sensible defaults plus a machine section (window, threshold, poll cadence), a workflow section (repo list, mail folder, admin repo path, caps), and an agent section (model, steps cap); validated at start-up with fail-fast, human-readable errors, because every deployment difference (repos, folders, thresholds) must be tunable without code edits (own analysis).
  - **[Decision: secrets]** Value = secrets (GitHub PAT) only via environment variables / `.env` with 0600, never in the config file or git, because the config is committed while secrets are not (research: /workspace/Research/home/email-m365-imap-oauth2-findings.md — credential handling pattern; own analysis).
  - **[Decision: state]** Value = a per-workflow durable state store (JSON) in a gitignored state area, keyed by stable identities (todo: repo + branch + commit SHA + path + line; email: Message-ID), because re-runs are the norm under a timer and every workflow must be idempotent (own analysis).
  - **[Decision: agent runner]** Value = one shared wrapper that launches `opencode run --agent <name> --model <configured> --dir <sandbox>` with a hard timeout and captures the JSON event stream into the run log, because both workflows need identical budgeting (agent `steps` cap), timeouts, and auditability, and `opencode run` exposes exactly these knobs (verified `opencode run --help` 2026-10-14; budgeting: /workspace/Research/ai-agent-workflow/agent-token-budget-steps.md).
  - **[Decision: agent definitions live in the global OpenCode config, not this repo]** Value = the purpose-built agents (`oc-todo-resolver`, `mail-keeper`) + their skills are defined in `~/.config/opencode/agents/` + `skills/` (versioned in the `oc_config` git repo) and referenced by name from this repo's runner, because (a) agent discovery follows the session directory — the workflow launches sessions with `--dir` targeting the vault / maildir / worktrees, where a project-scoped agent from `agentic_scripts` would not resolve (customize-opencode skill; verified `opencode run --dir` 2026-10-14); (b) the mail-keeper design requires interactive Task-tool dispatch from *any* session ("check mail", "draft a reply to X"), which only a global agent supports (research: /workspace/Research/ai-agent-workflow/mail-keeper-agent-design.md); (c) the user's 8 existing purpose-built agents establish global `agents/` as the single source of truth, and the agent-config-pattern skill forbids defining the same agent name in two places. Setup verifies the required agents exist and fails fast with a clear message if not (own analysis). Agents carry `steps` caps (research: /workspace/Research/ai-agent-workflow/agent-token-budget-steps.md).
- **Acceptance criteria:**
  - Missing or invalid configuration aborts start-up with a message naming the offending field.
  - Killing a run mid-flight and re-invoking never duplicates side effects (state is consulted before any action).
  - Both workflows import the same gate, lock, state, git, and agent-runner primitives; no workflow contains its own timer or lock logic.

### Task 3: OC-Todo Resolver Workflow
- **Goal:** For every configured GitHub repo, find every `OC-todo:` comment on every branch; for each one not already handled, have the agent produce a fix in a sandboxed worktree; commit, push a branch, and open one PR per todo that a human can review and merge.
- **Why this approach:**
  - **[Decision: scan = local clone + per-branch grep]** Value = full local clone (all remote branches) and `git grep` per branch, because the GitHub code-search API only covers the default branch, caps files at 384 KB, and is rate-limited to 10 req/min → [GitHub REST search docs](https://docs.github.com/en/rest/search/search); a local clone is deterministic, offline, and branch-complete (own analysis).
  - **[Decision: pattern]** Value = the strict, case-sensitive canonical marker `OC-todo:`, because the user chose the canonical form over a case-insensitive broad pattern (2026-10-14); matching is limited to text files with standard binary/build exclusions (own analysis of the marker's usage in local repos).
  - **[Decision: sandbox]** Value = one git worktree per todo, branched from the branch containing the todo, so concurrent todos and repos never share a checkout and no work happens on a shared clone's branches (own analysis; worktrees keep the full-clone history available to the agent).
  - **[Decision: agent scope]** Value = deterministic Python does clone/fetch, scanning, worktree setup, commit, push, and PR creation; the OpenCode agent only edits code inside the worktree (implement the todo, delete the `OC-todo:` comment — unless the comment or an `oc-original`-style note instructs keeping it — and run the project's test command if one is configured), because git/PR mechanics must be exact and auditable while code understanding is the agent's job (own analysis; `oc-original` convention observed in local repos, e.g. /workspace/Latex/Relative-localisation-tutorial-slides/slides/introduction/06_global_localisation.tex).
  - **[Decision: output = one PR per todo]** Value = push to a dedicated branch and open a PR against the branch that contained the todo, with the PR body quoting the exact comment, file, line, and the agent's summary, because the user chose review-before-merge over auto-push (2026-10-14); PRs are created via the GitHub REST API with the configured PAT because `gh` is not installed (verified 2026-10-14).
  - **[Decision: idempotency]** Value = a todo is skipped when its state says a PR was already opened, or an existing PR is found for the todo's dedicated branch; merged-and-comment-gone todos flip to resolved on the next scan, because the timer will re-scan forever (own analysis).
  - **[Decision: caps and failure]** Value = per-run caps (max todos per repo, agent `steps` cap, hard timeout) and retry-on-next-run semantics: a failed todo is recorded with its error and re-attempted on the next gate-open run, never leaving a partial push, because quiet windows are bounded and a hung agent must not block the schedule (research: /workspace/Research/ai-agent-workflow/agent-token-budget-steps.md — `steps` as the stop-and-report mechanism).
- **Acceptance criteria:**
  - Given a fixture repo with two `OC-todo:` comments on two different branches, one gate-open run produces exactly two PRs, each targeting the branch that contained its todo.
  - Each PR body quotes the exact `OC-todo:` comment text, names the file and line, and summarizes the change; the diff removes the comment (unless a keep-instruction applies).
  - Re-running with no repo changes opens zero new PRs; after merging a PR, the next run marks the todo resolved and does not reopen it.
  - An agent run that times out or exhausts `steps` leaves the todo in a failed/retry state, logs the reason, and the next run re-attempts it.
  - No workflow ever pushes to a protected or pre-existing branch — only freshly created per-todo branches are pushed.

### Task 4: Mail-Keeper Workflow
- **Goal:** Index the local maildir backup into a full-text database with a search CLI; on each gate-open run, triage new mail, fill the admin vault with provenance-tagged notes and tracked todos, and write draft replies as local files (never sent) — vault changes committed on a feature branch per git-workflow for human review.
- **Why this approach:**
  - **[Decision: reading layer = FTS5 index + CLI, never raw file reads]** Value = one-shot maildir→SQLite FTS5 index (message-id, folder, date, from/to/cc, subject, extracted text, attachments, flags) plus a `threads` table built from References/In-Reply-To and a thin `mail-search` CLI (query, sender, folder, date range, thread), because a measured 1,500-message INBOX sample is 331 HTML-only / 58 plain / 1,111 multipart (typical Outlook) — body text is not greppable in raw files and one CLI call replaces thousands of file reads (research: /workspace/Research/ai-agent-workflow/mail-keeper-agent-design.md).
  - **[Decision: new-mail detection]** Value = per-folder cursors (last processed message-id/date) plus the existing processed log at `/workspace/Obsidian/config/email-processing-log.jsonl` (the v1 `process_emails.py` contract), so any number of re-runs never double-process; malformed/undecodable messages are logged and skipped without aborting the batch (research: design doc; own analysis).
  - **[Decision: triage before writing]** Value = classify each new message noise/info/action/urgent with importance heuristics (sender tracked in `people/` or ORBIT people notes, action verbs, deadlines, active-project keywords, reply-to-me threads); only info/action/urgent produce vault writes; noise is logged only, because a 13k-message history must not be distilled into the vault (research: design doc — taxonomy validated against real senders).
  - **[Decision: vault fill with provenance]** Value = the agent writes only markdown into the existing vault structure — ORBIT mail → `projects/ORBIT/00_Project_management/{01_Meetings, 02_Reporting, 03_Communications}.md`, people → `people/<Name>/`, tasks → `todos/active.md` (existing sections: Projects, Funding & Grants, Waiting On) — and every mail-derived edit carries a `*(from: X, "Subject", YYYY-MM-DD, msg-id)*` tag so edits are auditable and reversible, because the vault defines the information architecture and agent writes must be traceable to the source message (research: design doc).
  - **[Decision: drafts local, never sent]** Value = one draft per thread at `mail/drafts/<date>_<thread-slug>.md` inside the gitignored mail area (local-only, never committed): full headers, original body, suggested reply — with the reply style few-shot-sampled from 3–5 of the user's own Sent Items (2,947-message corpus); no SMTP in scope, a Graph-send step is a later explicit opt-in, because the mailbox is not part of the repo (user, 2026-10-14) and drafts are proposals requiring human approval (research: design doc).
  - **[Decision: agent + skill placement]** Value = `mail-keeper` agent + skill in the global OpenCode config (`~/.config/opencode/agents/mail-keeper.md`, `skills/mail-keeper/`), versioned in the `oc_config` repo — same rationale as Task 2's agent-definition decision (discovery follows the session directory; interactive dispatch from any session; single source of truth alongside the existing 8 agents) (customize-opencode skill; research: design doc).
  - **[Decision: batched agent invocation]** Value = one `mail-keeper` invocation per gate-open run over the new-mail manifest (not per message), with `steps` cap and hard timeout, because per-message launches waste context setup and the agent needs the whole batch to dedupe overlapping follow-ups (research: design doc; /workspace/Research/ai-agent-workflow/agent-token-budget-steps.md).
  - **[Decision: guardrails]** Value = `INBOX/FU-Admin/PhD_applications/` (candidate PII) excluded from triage, drafts, and commits by default (explicit request only); the mail backup is read-only input — never written, moved, or renamed — keeping the 4.4 GB corpus local-only behind the gitignore (research: design doc).
  - **[Decision: vault commit policy — OPEN, user confirmation requested]** Value (recommended) = commit vault changes on a feature branch per run (`OC:` prefix), push, no auto-merge — human reviews before merge, because the design doc mandates git-workflow for vault writes and LLM-authored edits plus the PII guardrail argue for a review gate; this supersedes the earlier draft's direct-push-to-current-branch recommendation (research: design doc; git-workflow skill).
- **Acceptance criteria:**
  - First run builds the FTS5 index over all 13,088 messages; `mail-search` returns a known sender's thread by name/folder/date query.
  - A new message added to the backup (or a test folder) plus a `--force` run produces: a triage record, provenance-tagged vault note updates where applicable, a new todo line (or a logged decision that none is warranted), a draft file in `mail/drafts/`, and an `OC:`-prefixed commit on a feature branch that is pushed.
  - Re-running with the same mail produces zero duplicate vault edits, todos, or drafts.
  - Mail under `INBOX/FU-Admin/PhD_applications/` never appears in vault edits, drafts, or commits under default configuration.
  - The mail backup tree is byte-identical before and after any run (verified with a Python directory walk, not `find` — see Notes).
  - No mail is ever sent (no SMTP credentials or send tooling anywhere in the workflow).
- **Build order (research: design doc):** (1) indexer + `mail-search` CLI, (2) a real `email-routes.md` (the current file is placeholder; top-sender candidates extractable from the index), (3) `mail-keeper` agent + skill in the global config, (4) live sync — fill the IMAP `.env` or switch to Microsoft Graph delta-token sync (better for agents: JSON, `$search`, incremental).

### Task 5: Setup, Ops & Smoke Test
- **Goal:** One setup script brings a fresh environment up; a documented smoke test proves both end-to-end paths without waiting for the gate.
- **Why this approach:**
  - **[Decision: setup idempotency]** Value = the setup script detects systemd vs cron (mirroring the detection logic already in /workspace/scripts/email-sync/setup-timer.sh), installs the cron package (absent, verified) and registers the 30-minute crontab entry (idempotent), syncs the `uv` environment, checks required env vars, verifies the admin repo clone, and verifies the required global OpenCode agents exist (`oc-todo-resolver`, `mail-keeper`) — failing fast with a clear message if not — safe to re-run after container restarts, because this container has no init system to restart services for us (verified 2026-10-14; prior art: email-sync setup-timer.sh; own analysis).
  - **[Decision: smoke test]** Value = `--force` runs against a local fixture repo (with planted `OC-todo:` comments on multiple branches) and a fixture `.eml`, asserting the Task 3/4 acceptance outputs, because gate-dependent behavior must be verifiable on demand (own analysis).
  - **[Decision: documentation]** Value = a README front-loading what/why, the config reference, the env-var list, and how to (re)install the timer, because future workflows and future-you will onboard via the README (research: /workspace/Research/ai-agent-workflow/repo-file-conventions-best-practices.md — README structure guidance).
- **Acceptance criteria:**
  - On a clean environment, one setup run + config + env vars → the next gate-open run (or `--force`) executes both workflows correctly.
  - The smoke test passes end-to-end (fixture PRs created, fixture mail processed) and can be re-run without side effects on real repos (fixture-only).
  - Re-running setup on an already-configured machine changes nothing and reports that state.

## Alternatives Considered

1. **GitHub code-search API instead of local clones** — Rejected: default-branch-only, 384 KB file cap, 10 req/min → [GitHub REST search docs](https://docs.github.com/en/rest/search/search).
2. **Resident daemon polling load** — Rejected by user (chose timer + self-check, 2026-10-14); the timer-agnostic entry point keeps the option open.
3. **Raw `.eml` scan + stdlib `email` parser (initial draft of this plan)** — Superseded by the 2026-10-14 design doc: the measured MIME mix (331/1500 HTML-only) makes raw bodies non-greppable and 13,088 messages makes per-file reads impractical → FTS5 index + `mail-search` CLI (research: /workspace/Research/ai-agent-workflow/mail-keeper-agent-design.md).
4. **Direct IMAP/OAuth2 reading inside the workflow** — Deferred: a v1 IMAP pipeline already exists separately (/workspace/scripts/email-sync, currently OFF) and the live-sync choice (IMAP `.env` vs Microsoft Graph delta-token sync) is still under user research; the FTS5 index works on the local backup either way (research: design doc; /workspace/Research/home/email-m365-imap-oauth2-findings.md).
5. **Auto-push / auto-merge for OC-todo fixes** — Rejected by user (chose one PR per todo for human review, 2026-10-14).
6. **Agent definitions inside `agentic_scripts` (project-scoped)** — Rejected: agent discovery follows the session directory (`opencode run --dir`), and workflow sessions target the vault/maildir/worktrees where a project-scoped agent would not resolve; interactive Task dispatch from other projects would also break; the global config (`oc_config` repo) is the established single source of truth for the user's 8 existing agents (customize-opencode skill; agent-config-pattern skill).
7. **Direct push to the vault's current branch (initial draft of this plan)** — Superseded by the design doc's git-workflow mandate: feature branch per run, push, no auto-merge (pending user confirmation — see Task 4).
8. **Raw LLM API calls instead of OpenCode CLI** — Rejected: loses the reusable agent/skill/config infrastructure and the `steps` stop-and-report budgeting that headless runs rely on (research: /workspace/Research/ai-agent-workflow/agent-token-budget-steps.md).
9. **CPU-idle-based gating** — Superseded by the user's hybrid window+load choice (2026-10-14).
