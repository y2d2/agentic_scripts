# Task 5b: Batch cap, cross-folder new-first, true per-folder frontier

**Purpose:** Follow-up to Task 5 (same session). Orchestrator code review of Task 5's implementation found three contract violations the fixture tests could not see. Fix them surgically in `src/agentic_scripts/workflows/mail_keeper.py` (+ test updates). The public behavior (newest-first, 1-year floor, ≤10/run, new mail never starved, no loss) stays exactly as the user decided on 2026-10-23.

## The three defects (verify each against the code before fixing)

1. **Batch cap violated (≤10 → up to 20).** In `MailKeeper.run`, `merged = [*manifest, *deferred]` (dedup) is what goes to the brief, the processed log, and the cursor update. The previous run's `deferred` (up to 10 cap-overflow entries) is therefore delivered IN ADDITION to this run's manifest (up to 10) → the agent can receive up to 20 messages, the log can gain 20 records, and the cursor moves over 20. **Fix:** the deferred is re-injected into the CANDIDATE POOL (not on top of the manifest); the ≤`MAX_BATCH` cap is re-applied to the final batch.
2. **Cross-folder new-mail starvation.** `_detect` collects per folder (INBOX first) with a shared global KEPT budget: INBOX's backfill history (≈2.5k live) can consume the entire `2*MAX_BATCH` KEPT budget before smaller folders' NEW mail is collected → new mail in ORBIT/Admin/Students/Spin-off/VICON_ICT waits the whole INBOX backfill. **Fix:** two-pass global collection — pass 1 collects EVERY folder's `new_set` (folder order, each newest-first), pass 1.5 merges the deferred (already-kept entries: no re-`show`, de-duped by id), pass 2 collects EVERY folder's `hist_set`; ONE shared global KEPT budget (`2*MAX_BATCH`) across all passes; `batch = pool[:MAX_BATCH]`, `deferred_new = pool[MAX_BATCH:]` (manifest order = pool order: all new first, then deferred, then all history).
3. **`back` never advances + per-folder cursor corruption.** (a) The update `if min_ts < back_last and min_ts >= floor` never fires because `back_last` starts at the floor and the min-rule keeps it there — `back` is pinned to the floor forever (the processed log is de-facto the frontier: correct but late-phase-costly — each run re-walks the whole processed pile, up to ~3.5k `show`s ≈ 30+ min/run in the late phase). (b) The cursor loop applies the GLOBAL batch `max_ts`/`min_ts` to EVERY folder's cursor (a batch member of folder A moves folder B's boundaries). **Fix:** true per-folder frontier: for each folder PRESENT in the batch: `new_f = max(new_f, max ts of the batch's entries in folder f)`; `back_f = min(back_f, min ts of the batch's entries in folder f with ts < old new_f)` (history-kind only — entries below the folder's PREVIOUS `new` boundary; if a folder has no history-kind batch members, `back_f` is unchanged). Folders absent from the batch keep both boundaries. The deferred mechanism stays loss-safe under this: overflow entries sit at/below the new frontier (history-kind) or below `new` (new-kind) and are carried by the `deferred` list, re-injected in pass 1.5.
